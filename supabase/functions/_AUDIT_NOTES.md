# Edge Function audit notes (READ-ONLY audit, 2026-09)
Format: slug | verify_jwt | own authz | tenancy | .online dep | finding

- verify-otp | false | none (userId+otp from body, matched against admin_telegram_otps hash) | OK (hash must match row for that user_id) | none | attempts>=5 check happens AFTER a successful hash match, so it never throttles wrong guesses; throttling relies on rpc increment_otp_attempts. LOW.
- verify-2fa | true | JWT sub parsed WITHOUT signature check (gateway verifies) | n/a | none | PROVEN: `tempSecret` is supplied by the CALLER and the TOTP is checked against it. Caller controls both secret and code => can always obtain {verified:true}. Only meaningful if the enrollment/login consumer trusts this boolean. Rate limiting is real (twofa_rate_limits).
- generate-2fa-secret | true | none | n/a | issuer string "Mad3oom.online" | cosmetic only: appears as the account label in authenticator apps. Changing it does not invalidate existing secrets but relabels new enrollments.
- gemini-proxy | true | NONE beyond gateway JWT | BROKEN | none | PROVEN CROSS-TENANT READ: `userId` comes from the request BODY, then a service_role client reads profiles.full_name and the 3 latest tickets (number/status/priority) for that id and returns them via the LLM reply. Any authenticated user can read any other user's ticket metadata + full name. HIGH.
- landing-contact | false (intentional public form) | honeypot + per-email rate limit | n/a | FROM no-reply@mad3oom.online, TO support@mad3oom.online | DOMAIN DEP: Resend verified-domain + destination inbox both on .online. Breaks on retirement.
- send-ticket-email | false | own authorize(): internal_service_secrets.send_ticket_email_internal OR JWT+role in (admin,support) | n/a | ALLOWED_SENDERS = support@/no-reply@/info@mad3oom.online; EMAIL_FROM default info@mad3oom.online | DOMAIN DEP (hard-coded allowlist). Note super_user is NOT allowed. `customer_email` and `message` are caller-controlled HTML -> admin/support can send arbitrary mail from a Mad3oom address.
- huggingface-chatbot | false | NONE | no DB access | none | PROVEN: fully unauthenticated public LLM proxy burning HUGGINGFACE_API_KEY. No tenant data exposure; cost/abuse risk only.
- send-whatsapp | false | API token (api_tokens) + scope whatsapp:send | OK (resolveIntegration filters by token.user_id AND phone_number_id) | none | SHARED CREDENTIAL: getWhatsAppAccessToken() ignores integration.access_token and always returns the platform-wide env WHATSAPP_TOKEN (explicit TODO in code). Rate limit 60/min is fail-open on count error.
- create-template | false | own check: JWT + role in (admin,support) | platform-level WABA | none | OK. super_user excluded.
- meta-webhook | false | HMAC x-hub-signature-256 verified ONLY IF META_APP_SECRET is set (fail-open when unset — NOT ENOUGH EVIDENCE on env) + hub.verify_token on GET | platform-wide whatsapp_templates (no owner column used) | none | no role/hierarchy writes. Not Phase 0 relevant.
- get-attachment-url | true | JWT + strict `role !== "admin"` reject | admin-only | none | SAFE. Notably the ONLY correct pattern: pure role='admin', no email allowlist, no super_user.
- create-subdomain | false | JWT + strict role==='admin' (super_user EXCLUDED) | admin acts on behalf of client_user_id (validated to exist) | **ROOT_DOMAIN = "mad3oom.online" hard-coded** | MAJOR DOMAIN DEP: creates a real Cloudflare CNAME in CLOUDFLARE_ZONE_ID (the .online zone) pointing at cname.vercel-dns.com, then attaches `<name>.mad3oom.online` to the Vercel project. The whole white-label subdomain feature is bound to .online. Migration = change ROOT_DOMAIN + CLOUDFLARE_ZONE_ID + re-create every DNS record + re-add every Vercel domain.
- request-subdomain | false | JWT, any authenticated user; writes ONLY user_id = own auth.uid() | self-scoped, correct | ".mad3oom.online" hard-coded in 2 user-facing strings | DOMAIN DEP (cosmetic strings) + the queue it feeds is consumed by create-subdomain above.
- check-subdomain-status | false | NONE (fully public by design — white-label page bootstrap) | reads subdomain_requests by name | ".mad3oom.online" in a comment only | PROVEN INFO EXPOSURE: for any active subdomain an anonymous caller gets back the owner's `user_id` (profile UUID) plus logo_url. Enumerable. Low-moderate: UUID alone is not a credential, but it hands an attacker a valid target id for other body-parameter bugs (see gemini-proxy).
- manage-subdomain | false | JWT + strict role==='admin' | admin-wide (list/rename/reassign/suspend/delete/approve/reject); every action written to subdomain_activity_log with performed_by + email | **ROOT_DOMAIN = "mad3oom.online"** hard-coded + several .online strings in notifications | (a) MAJOR DOMAIN DEP, same as create-subdomain. (b) PROVEN PostgREST filter injection in action=search_clients: `.or(\`email.ilike.%${q}%,full_name.ilike.%${q}%\`)` interpolates the caller-supplied `q` straight into the filter grammar — a `q` containing `,` or `)` rewrites the predicate. Admin-only, so severity is limited to an admin widening their own profile query, but it is a real injection.
- regenerate-api-token-secret | true | JWT; ownership enforced by reading api_tokens through the RLS-scoped user client BEFORE updating via service_role by id | CORRECT (best pattern in the codebase) | none | SAFE, conditional on api_tokens SELECT policy being owner-scoped. New bearer = mad3oom_bt_ + 32 random bytes; secret = mad3oom_sk_ + 40 base62. Regeneration also silently sets revoked_at=null, is_active=true — i.e. it UN-REVOKES a revoked token. Minor.
- ai-probe-temp | true | n/a | n/a | none | DEAD CODE. Returns 410 unconditionally; body says it should be deleted from the dashboard. No DB or key access. (No action taken — read-only audit.)
- check-dns-status | false | **NONE** | operates on any subdomain_requests row by id from the body | none | PROVEN UNAUTHENTICATED WRITE: an anonymous caller supplying a row UUID can flip status 'propagating' -> 'success', stamp activated_at, and insert a notification for that row's owner. Bounded by an actual HTTPS HEAD check against the domain, so it cannot activate a domain that is not really live; impact is unauthorized state transition + notification spam, not takeover. Row ids are UUIDv4 (not enumerable) but ARE returned to admins and to the client in create-subdomain's response.
- whatsapp-graph-request | true | JWT verified via anon client (auth.getUser), then integrations filtered `.eq("user_id", userId)` | CORRECT tenancy | none | Uses the TENANT's own decrypted Meta token (AES-GCM-256, WHATSAPP_TOKEN_ENC_KEY) — unlike send-whatsapp which uses the platform-wide env token. FINDING: explicit `TODO(token-migration)` legacy fallback to the PLAINTEXT `integrations.access_token` column when `encrypted_access_token` is null. Any surviving row with a plaintext Meta token is a stored-credential exposure. Needs a read-only count.
- whatsapp-phone-status | true | same pattern, `.eq("user_id", userId)` | CORRECT tenancy | none | encrypted-only (no plaintext fallback). SAFE.
  -> READ-ONLY DB EVIDENCE (public.integrations): wa_rows=3, wa_encrypted_token=3, wa_plaintext_token=2, wa_plaintext_only=0.
     PROVEN: the legacy plaintext fallback in whatsapp-graph-request is currently UNREACHABLE (every row has encrypted_access_token),
     but 2 of 3 rows STILL HOLD a plaintext Meta access token at rest in `integrations.access_token`. Cleanup candidate. No action taken.
- telegram-connect-bot | true | JWT (auth.getUser) then all writes keyed to `.eq("user_id", userId)` | CORRECT tenancy | none | Stores the customer's BotFather `bot_token` in PLAINTEXT in customer_telegram_bots (no encryption, unlike the WhatsApp path). Registers a per-user webhook `/functions/v1/telegram-webhook/<userId>` with a per-row `webhook_secret` as Telegram's secret_token — good design. FINDING: plaintext bot-token storage; also whether customer_telegram_bots RLS hides bot_token from other tenants is a separate check.
- telegram-webhook | false (correct — Telegram cannot send our JWT) | per-user `webhook_secret` compared against X-Telegram-Bot-Api-Secret-Token | CORRECT (user_id comes from the URL path but the secret is looked up FOR THAT user, so a wrong user_id yields a mismatched secret) | none | SAFE. Non-constant-time `!==` on the secret — negligible over the network.
- register-whatsapp | true | JWT + `.eq("user_id", userId)` + phone_number_id must match one of the caller's own rows | CORRECT tenancy | none | encrypted-only. Generates/stores an encrypted 6-digit verification PIN. SAFE.
- whatsapp-session | false | **`Bearer <apiKey>` is matched by plaintext EQUALITY against `integrations.access_token`** — i.e. the tenant's raw Meta access token IS the API key | user_id derived from the matched row, so once authenticated the scoping is correct | none | HIGH / PROVEN DESIGN FLAW: (1) no hashing — the credential is stored and compared in cleartext; (2) no rate limiting and no scopes, unlike the api_tokens path; (3) it then calls Graph with that same plaintext token. Cross-links to the integrations evidence above: 2 of 3 rows still carry a plaintext access_token, so this endpoint is LIVE for exactly those 2 tenants and dead for the third. Nulling the legacy plaintext column would both remove the at-rest exposure AND disable this endpoint — check for callers before doing so. 24h session-window enforcement itself is correct.
- chat-bot-reply | true | JWT; session ownership PROVEN via an RLS-scoped read of chat_sessions BEFORE any service_role write | CORRECT | none | Tickets and chat_messages are written with user_id/sender_id from the JWT, never from the body. getMyTicketsReply / getMySubscriptionReply both filter `.eq("user_id", userId)`. SAFE — this is the correct counter-example to gemini-proxy.
- inbound-email-webhook | false (correct for a provider webhook) | Svix HMAC verified ONLY IF RESEND_WEBHOOK_SECRET is set; otherwise it logs a warning and processes the request. Signature comparison is non-constant-time `.includes()` | service_role insert into mailbox_emails; links to a profile by `.eq("email", fromEmail)` | none literal, but the inbound address is on the Resend-verified domain (= .online today) | FAIL-OPEN WEBHOOK if the secret is unset — NOT ENOUGH EVIDENCE on the env value. If unset, anyone can POST fabricated inbound email into the admin mailbox and attach it to any profile by spoofing `from`.
- resend-inbound-webhook | false | identical Svix logic, same fail-open | identical writes | same implicit domain dep | DUPLICATE of inbound-email-webhook — two live functions doing the same job. One is almost certainly dead; only one can be wired in the Resend dashboard. Needs confirmation before either is removed. No role/hierarchy writes in either.
- oauth-discovery | false (must be public, RFC 8414) | none | n/a | **issuer = "https://mad3oom.online"** + authorization/token/registration endpoints + service_documentation, ALL hard-coded .online | CRITICAL DOMAIN DEP: the OAuth *issuer identity* is `https://mad3oom.online`. In OAuth/OIDC the issuer is an identity, not just a URL — changing it invalidates every already-issued token/consent that pinned it and forces every MCP client to re-discover and re-consent. This is the single hardest .online dependency found. Also confirms `admin:full` is an advertised, grantable scope alongside subscriptions:read/write/renew/cancel/plans.
- oauth-protected-resource | false (must be public, RFC 9728) | none | resource = ${SUPABASE_URL}/functions/v1/mcp (env-derived, migration-safe) | authorization_servers: ["https://mad3oom.online"], resource_documentation same | DOMAIN DEP, must change in lockstep with oauth-discovery's issuer.
- mcp-server-info | true | JWT + `userClient.rpc("is_admin")` | admin-wide | none | Uses the DB `is_admin()` — which is role='admin' OR email IN (support@,info@ mad3oom.online). So this endpoint is one of the ~consumers that inherits the Founder email allowlist. Writes advanced_settings.mcp_server_tools (enable/disable MCP tools globally). Phase 0 relevant: it is affected by any change to is_admin().
- oauth-register | false (RFC 7591 dynamic registration must be open) | none, by design; rate-limited 5/hour/IP via oauth_rate_limit_hits; every attempt logged to oauth_client_registrations_log | n/a | none | ACCEPTABLE. redirect_uris forced to https (localhost/127.0.0.1 exempt). client_secret stored as SHA-256 hash. Anyone on the internet can create an oauth_clients row — that is what dynamic registration means; the actual gate is the user consent step (oauth-authorize-approve).
- oauth-token | false (RFC 6749 token endpoint) | client auth (Basic or POST) with timing-safe hash compare; PKCE S256 verified timing-safe; code single-use (used_at); redirect_uri and client_id must match the code; refresh rotation revokes both the old refresh token and its api_tokens row | tokens bound to authCode.user_id | none | STRONG. No weakness found. NOTE: granted scopes come verbatim from `authCode.scope`, so the whole authorization surface (including `admin:full`) is decided upstream in oauth-authorize-approve — that is the function that must be proven not to allow self-elevation.
- oauth-authorize | false (RFC 6749 authorize endpoint) | none by design; rate limited 60/min/IP and 20/min/client+IP; PKCE S256 MANDATORY; redirect_uri must be in the client's registered list | n/a | **CONSENT_PAGE_URL = "https://mad3oom.online/admin/oauth-consent.html"** hard-coded | DOMAIN DEP (3rd in the OAuth chain). Validation itself is correct — no open redirect (redirect_uri is checked against oauth_clients.redirect_uris before the 302).
- mcp-invoke-tool | true | JWT + `can_use_mcp_client()` RPC, then invokeTool(adminClient, userData.user.id, ...) — ownerId always from the JWT, never from the body | CORRECT; resolveTool() is owner-scoped and returns "غير مفعّلة لهذا المالك" otherwise | none | SAFE. Per-connection secrets are encrypted at rest and decrypted per call. 23 source files mirrored locally.
  -> DB EVIDENCE: can_use_mcp_client(p_user_id) = has_chatbot_entitlement(p_user_id) = `whatsapp_enabled = true OR role IN ('super_user','admin')`.
     So super_user gets the MCP client as an ENTITLEMENT. That is acceptable (it is a feature flag, not cross-tenant access) and is distinct from the ~41 policies where super_user wrongly grants GLOBAL data visibility.
  -> DB EVIDENCE (re-confirmed): is_admin() = `role = 'admin' OR email IN ('support@mad3oom.online','info@mad3oom.online')`.
- mcp-oauth-start | true | JWT + `is_admin()` RPC, AND the connection row must match `.eq("owner_id", userData.user.id)` | CORRECT (admin + owner) | none | SAFE. state = `<connection_id>.<uuid>`.
- mcp-oauth-callback | false (browser redirect from the external provider — correct) | `state` must equal the stored `oauth_state` for that connection; cleared after use | connection resolved from the state, not from a caller-supplied id alone | **ADMIN_MCP_PAGE_URL = "https://mad3oom.online/admin/mcp.html"** hard-coded | DOMAIN DEP (4th). Tokens encrypted AES-GCM with MCP_ENC_KEY (key = SHA-256 of the secret, so any secret length works). Logic is sound.
- test-integration-connection | true | JWT, then an RLS-scoped read of external_integrations BEFORE the service_role read of the encrypted credentials | CORRECT (same good pattern as regenerate-api-token-secret) | none | Credentials AES-GCM with INTEGRATIONS_ENC_KEY. LOW finding: provider "webhook" POSTs to `creds.url` verbatim — owner-supplied SSRF from the platform's egress (can reach internal endpoints the function can see). Bounded to a URL the owner stored themselves.
- sie-channel-telegram | false | POST path: Telegram secret_token verified inside the adapter (fails closed if BOT_TOKEN or WEBHOOK_SECRET missing -> 500). **GET path: NO AUTH AT ALL** | service_role, but writes carry an explicit user_id resolved from channel_identities | none | TWO FINDINGS: (1) the unauthenticated GET self-check returns bot_username, the registered webhook URL, Telegram's last error, pending count, and `linked_telegram_chats` (a live customer count) — anonymous operational info disclosure; (2) that same anonymous GET calls autoRegisterWebhook(), which re-points the Telegram webhook whenever channel_secrets.telegram_autoregister='true' — anyone who can GET the URL can trigger it during that window. Also a SUPPLY-CHAIN dependency: the engine is imported at deploy time from cdn.jsdelivr.net/gh/moudabdelwahab/sie pinned to commit 8252e577 (SHA-pinned = immutable, which is the right call).
